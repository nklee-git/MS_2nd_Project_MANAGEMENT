## 서론 — 왜 이 문서가 필요한가

협업허브는 지금까지 두 종류의 자료가 따로 존재했다: (1) [[73-functional-spec-all-tabs]]·[[72-dashboard-spec]]엔 "게시물/공지사항/파일/채팅 4개 하위탭, 게시물·채팅만 이번 스코프"라는 **화면 스펙**만 있고, (2) [[53-virtual-team-profiles]] 3절엔 시나리오 A~I·`MENTION` 필드까지 상당히 구체적인 **로직 초안**이 이미 있었는데, 이 둘이 한 번도 연결된 적이 없다. 그 결과 "Teams 연동하면 되겠지"라는 말로 뭉뚱그려지고, 실제로 반려 클릭 한 번이 어떤 테이블에 뭘 쓰고 누구에게 어떤 형태로 도달하는지는 아무도 정의한 적이 없었다.

이 문서는 그 갭을 메운다 — **이번 스코프(게시물+채팅)는 실제로 구현 가능한 수준까지 상세화**하고, **백로그(공지사항·파일·멘션 양방향·승인 스텝퍼)는 지금 만들진 않지만 나중에 다시 펼치기만 하면 되는 수준까지 스펙을 남겨둔다.** 마침 9/19 회의 안건 6이 정확히 이 지점("Collab 테이블 신설 여부·시점")을 묻고 있어서, 이 문서의 2-3~2-7절이 그 결정에 바로 쓰이도록 구성했다.

### 2-2. 설계 원칙

1. **엔티티는 최소로, 확장은 필드로.** [[25-execution-design]] "새 기술 안 늘림" 원칙을 따라 — `TASK`/`MENTION`/`ALERT_LOG` 3개를 각각 다 만들지 않고, 이번 스코프가 필요로 하는 것(반려 알림 피드)만 담는 테이블 하나로 시작해서 `source_type`으로 종류를 구분한다.
2. **엔드포인트는 최대한 늘리지 않는다.** [[25-execution-design]] 4절 "4개 제한, 늘리려면 문서 먼저 개정" 원칙 준수 — 아래 2-7절에서 실제로 몇 개가 늘어나는지 명시한다.
3. **상태 관리(읽음/해결)는 이번엔 안 한다.** 승인/반려처럼 "누가 언제 처리했는지"가 감사 대상인 액션이 아니라 단순 알림 피드이므로, MVP는 **생성(Insert)과 조회(Get)만** 있으면 충분 — 상태 전이는 승인 스텝퍼(`TASK`)가 붙는 Tier2로 미룬다.

### 2-3. 신규 엔티티 — `COLLAB_POST` (권장, 최민 9/18 제안 채택+확장)

기존 백로그의 `ALERT_LOG`(알림 이력)와 최민이 제안한 "Collab 테이블"은 사실상 같은 것을 가리킨다 — **`ALERT_LOG`를 별도로 만들지 않고 `COLLAB_POST`로 흡수**하는 걸 권장한다. `TASK`/`MENTION`은 이번엔 안 만들고 스키마만 아래 2-6절에 남겨둔다.

| 필드 | 타입 | 설명 |
| --- | --- | --- |
| `collab_post_id` | string (PK) | |
| `source_type` | Choice | `REORDER_REJECTED`(이번 스코프) — 향후 `WEEKLY_REPORT`/`KPI_THRESHOLD` 등 추가 가능(2-4절) |
| `sku_code` | string, FK → SKU | `ReorderRecommendation`이 sku_code를 PK로 쓰므로 그대로 재사용, 별도 조인키 불필요 |
| `reason_tags` | string | 반려 해시태그, 콤마join (예: `"#체형스펙수정"`) |
| `reason_text` | string, nullable | 자유입력 사유 |
| `target_user` | string | 라우팅 결과 담당자 (2-5절 표) |
| `target_role` | string | 담당자의 역할 표시용(예: "Technical Designer") |
| `message` | string | 자동생성된 알림 문구(2-4절 템플릿) |
| `created_at` | datetime | |

- **생성 시점**: `PATCH /api/reorders/{skuCode}` 로 `status=Rejected` 처리될 때 Service 레이어가 같은 트랜잭션 안에서 INSERT — 별도 엔드포인트 불필요.
- **삭제한 것**: `status`(안읽음/읽음/해결) 필드는 위 원칙 3에 따라 이번엔 뺐다. 필요해지면 그때 컬럼 추가(마이그레이션 비용 낮음).

### 2-4. 하위탭별 로직

**게시물 (이번 스코프)**
1. 반려 처리(B 로직, 기존 정리된 [[25-execution-design]] 그대로) → `COLLAB_POST` INSERT
2. `message` 필드는 아래 템플릿으로 자동생성(= [[72-dashboard-spec]] 결론의 "메시지 자동생성 vs 기존대화 검색" 질문에 대한 답: **자동생성 채택** — "기존대화 검색"은 `MENTION`이 실제 Teams 메시지를 가져오는 Tier2 기능이라 이번엔 할 수 없음):
   ```
   [재발주 반려] {styleName}({sku_code}) 발주 추천이 반려됐습니다.
   사유: {reason_tags}{reason_text가 있으면 " — " + reason_text}
   {태그별 행동유도문구, 2-5절}
   ```
3. 프론트: `GET /api/collab-posts` 결과를 카드 리스트로 렌더 — SKU/스타일명, 태그 칩, 담당자 이름, 생성일시, "Teams에서 보기" 버튼(딥링크, 아래)

**채팅 (이번 스코프, 딥링크만이지만 내용을 채운다)**
- 지금 스펙은 "Teams를 새 창으로 열기"까지만 정의돼 있고 어떤 링크인지가 없었다. Teams 딥링크는 수신자·프리필 메시지까지 URL 파라미터로 넣을 수 있다:
  `https://teams.microsoft.com/l/chat/0/0?users={target_user 이메일}&message={message 필드 URL 인코딩}`
- 즉 게시물 카드의 "채팅" 버튼을 누르면 **담당자와의 1:1 채팅이, 2-4절 템플릿 메시지가 이미 입력창에 채워진 채로** 열린다 — 새 인프라 없이 기존 `message` 필드 재사용만으로 되는, 이번 스코프 안에서 바로 되는 개선.

**공지사항 (Tier2, 백로그 — 스펙만)**
- 트리거 후보: [[53-virtual-team-profiles]] 시나리오 D(주간 매출 리포트, 매주 월 09:00 스케줄)·E(카테고리 매출 -20% 이상 하락)·F(분기 마감)
- 별도 테이블 불필요 — `COLLAB_POST.source_type`에 `WEEKLY_REPORT`/`KPI_THRESHOLD` 값만 추가하고, 프론트 "공지사항" 탭은 `GET /api/collab-posts?type=announcement`로 같은 테이블을 필터링해서 보여주면 됨(2-7절 엔드포인트 설계가 이걸 감안한 이유)
- **주의**: 이 트리거들은 [[22-feature-spec]] 3절 "부서별 다중 KPI 대시보드"와는 다르다(그건 화면을 늘리는 것, 이건 기존 게시판에 알림 한 줄 얹는 것) — Out of Scope 조항과 충돌 안 함

**파일 (Tier3, 백로그 — 스펙만)**
- 별도 저장/업로드 기능 없음(원칙: [[53-virtual-team-profiles]] 3-4절 "SharePoint 링크만 참조, 별도 저장 안 함" 그대로 재사용)
- `COLLAB_POST`에 `attachment_url`(nullable) 필드만 추가하면 "파일" 탭은 `attachment_url IS NOT NULL`인 레코드만 모아 보여주는 뷰 — 이번 스코프에 넣을 데이터가 없어서(반려엔 첨부파일이 없음) 지금은 빈 탭이 되므로 착수 안 함

### 2-5. 태그 → 담당자 라우팅 테이블 (신규 확정 제안)

지금까지 "#체형스펙수정 → 박지민" 예시 하나뿐이었던 걸 5개 전부 채운다. 전부 [[53-virtual-team-profiles]] 1절 R&R 근거로 매핑:

| 해시태그 | 반려 사유 해석 | 담당자 | 근거(R&R) | 행동유도문구 |
| --- | --- | --- | --- | --- |
| `#체형스펙수정` | 사이즈/패턴이 체형 데이터와 안 맞음 | 박지민 (Technical Designer) | "체형 패턴 설계, 샘플링 및 QC" | "→ 패턴 재검토 요청" |
| `#생산지연` | 공장 캐파/일정 문제 | 배주현 (SCM, 직진배송 풀필먼트팀장) | 3-1절 시나리오 C "생산 지연 승인 체인의 1차 판단자" | "→ 입고 일정 재확인 요청" |
| `#직진배송입고` | 입고/물류 리드타임 이슈 | 배주현 (SCM) | 동일 | "→ 입고 경로 확인 요청" |
| `#원가절감` | 원가구조상 수량/타이밍 부적절 | 박채영 (회계팀 파트장) | "OEM 공장 기성금/원단 대금 정산" | "→ 원가구조 재검토 요청" |
| `#긴급승인` | 반려하지만 예외적 상위 재검토 필요 | 김남준 (Brand Lead) | 3-1절 시나리오 B 고액발주 2·3단계 승인 | "→ 상위 재승인 여부 검토 요청" |

`#긴급승인`은 사실상 시나리오 B(고액 2단계 승인)의 진입점과 같다 — Tier2에서 `TASK` 승인 스텝퍼를 붙일 때 이 태그가 자연스럽게 그 체인의 트리거가 될 수 있다(2-6절).

### 2-6. 이번엔 안 만들지만 스키마는 남겨두는 것 (Tier2/3 로드맵)

| 항목 | 트리거 | 필요 엔티티 | 실제 쓰임 |
| --- | --- | --- | --- |
| Teams 양방향 동기화 | Teams 메시지 게시/대시보드 답장 | `MENTION` (필드 확정: [[53-virtual-team-profiles]] 3-4절, 그대로 채택) | 채팅 탭이 "딥링크"에서 "임베드형 대화"로 승격 |
| 승인 스텝퍼 | `#긴급승인` 태그 또는 `recommended_qty × unit_cost ≥ 5,000,000원` | `TASK`(task_type/requester/reviewer/status/sla_deadline, [[72-dashboard-spec]] 부록 D 초안) | 시나리오 B 고액 2·3단계 승인 체인 |
| 코멘트 스레드 | 게시물 카드에서 "논의 필요" 표시 | `TASK`와 동일 테이블 재사용 검토(스레드=task_type의 하위 유형) | 시나리오 G/H/I(신규 SKU 리뷰, 재고위험 대응회의) |

이 셋은 [[42-work-order-choimin]]·[[72-dashboard-spec]]가 이미 "스키마 확장 선행 필요"로 닫아둔 항목과 일치 — 이 문서는 그 판단을 재확인만 하고, **9/23 체크포인트 통과 후에만 착수**한다는 기존 원칙([[25-execution-design]] 서론)을 그대로 유지한다.

### 2-7. API 계약 영향 — 몇 개가 늘어나는가

[[25-execution-design]] 4-2절 "엔드포인트 4개, 늘리려면 문서 먼저 개정" 원칙 기준으로 정직하게 계산하면:

- **INSERT**: 새 엔드포인트 불필요 — 기존 `PATCH /api/reorders/{skuCode}` Service 로직 안에서 같이 처리
- **조회(게시물+공지사항+파일 공용)**: `GET /api/collab-posts?type=` **신규 1개 필요** — 하나로 세 탭을 다 커버(위 2-4절 쿼리파라미터 설계)
- **상태 변경(읽음/해결)**: 2-2절 원칙에 따라 이번엔 없음 → PATCH 추가 불필요

**결론: 5번째 엔드포인트 1개 추가가 불가피하다.** "늘리지 않는다"가 아니라 "1개만, 그것도 세 탭을 겸용해서 최소로 늘린다"는 것이 이 문서의 권장안 — 9/19 회의에서 이 1개 추가를 공식 승인할지만 결정하면 된다.

## 결론 — 9/19 회의 안건 6에 대한 권장안

1. **신설 여부**: 예. 단, `ALERT_LOG`가 아니라 최민 제안대로 `COLLAB_POST` 단일 테이블(2-3절 스키마)로 — 별도 `ALERT_LOG` 백로그 엔티티는 폐기하고 이 테이블로 흡수
2. **착수 시점**: 백엔드(테이블 1개 + INSERT 로직 + GET 엔드포인트 1개)는 지금 병행 가능한 저위험 작업으로 판단 — `ReorderRecommendation` 갱신 로직에 몇 줄 얹는 수준. **프론트 실데이터 연동(현재 샘플데이터 카드 → 실제 API 호출)은 9/23 체크포인트 이후로 순서를 늦춰도 데모에 지장 없음**
3. **엔드포인트 확장**: 5번째(`GET /api/collab-posts`) 1개 추가를 이 결정과 함께 승인 — [[25-execution-design]] 4-2절에 반영 필요
4. **부수 결정 2건도 이 문서에서 답함**: 메시지는 자동생성(템플릿) 채택 / "기존대화 검색"은 `MENTION` Tier2로 이관

### 아직 팀 확인이 필요한 것
- [ ] 태그→담당자 라우팅표(2-5절)가 실제 승인 화면 해시태그 5종과 완전히 일치하는지 (나경/최민) — [[22-feature-spec]] 결론엔 "드롭다운 4종"이라는 표현도 남아있어 5종/4종 표기가 문서마다 다름, 실제 구현 기준 확인 필요
- [ ] Teams 딥링크(`teams.microsoft.com/l/chat/...?users=&message=`)가 팀 M365 테넌트에서 실제로 프리필 메시지까지 여는지 1회 실사용 테스트 (최민)
- [ ] `COLLAB_POST`를 9/23 체크포인트 "풀 루프 1회 통과" 검증 항목에 포함시킬지, 아니면 통과 기준과 무관한 부가기능으로 둘지
