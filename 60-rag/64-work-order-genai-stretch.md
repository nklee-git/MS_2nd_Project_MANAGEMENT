## 서론

이 문서는 코어(카드 7필드 + 승인/반려 플로우)가 이미 완료된 뒤에 붙이는 **GenAI 스트레치 두 단계**의 작업지시서다. 순서가 중요하다 — ①이 배포·QA까지 끝나기 전에는 ②(MAI 후속 질의)에 손대지 않는다. [[21-system-model]] 부록 A에 이미 "완전히 분리된 독립 스트레치"라고 못박혀 있다.

**착수 조건**: 9/23 코어 체크포인트 통과 후에만. 통과 전이면 이 문서는 준비 자료로만 읽고 실제 구현은 시작하지 않는다 — 순서를 앞당기면 코어도 못 끝낸다는 게 이 프로젝트 전체의 원칙([[62-work-order-parkhyungjun]] 2-5절에도 동일하게 명시돼 있음).

### 1. 예측근거 자연어 설명 (Tier 1, 우선 착수)

**Step A. 근거 데이터 조회 (탐색)**
- ERD 관계(SKU → 판매속도 → 재고소진일 → 계절 민감도 → 프로모션)를 순회해서 근거 데이터를 모으는 쿼리 준비 — 이미 있는 ERD를 그대로 쓰는 것이라 별도 Graph DB는 만들지 않는다([[2-tech-research]] §6-2, GraphRAG류지만 신규 인프라 불필요)
- 조회 대상: 최근 N일 판매속도, 리드타임 대비 재고소진일, 카테고리별 계절 민감도 계수, 임박 프로모션 유무

**Step B. 프롬프트·출력 스키마 설계**
- Structured Output으로 제한: `{"summary": string, "key_factor": string, "confidence": number}` ([[2-tech-research]] §6-2 확정 스키마, 새 필드 임의 추가 금지)
- 프롬프트에는 Step A에서 모은 근거 데이터만 주입 — 모델이 근거 밖의 사실을 지어내지 않도록 컨텍스트를 좁게 유지

**Step C. Power Automate 플로우에 연결**
- 0절의 "호출 위치" 결정에 따라: (a) Power Automate 안 Azure OpenAI 커넥터 액션 추가, 또는 (b) `FashionAI.Api`에 새 엔드포인트 추가 후 그걸 호출하는 액션 추가
- 카드 반영: [[63-approval-card-template]]의 `FactSet` 아래에 `summary`를 보여주는 `TextBlock` 하나만 추가(참고용 1줄) — 기존 7필드·버튼 구조는 그대로 유지, 새 Dataverse 필드는 감사추적이 필요하다고 팀에서 판단할 때만 추가(기본은 카드에만 노출하고 영속화하지 않음)

**Step D. 검증 가드레일**
- 생성된 `key_factor`가 실제 피처 중요도 상위 3개 안에 있는지 규칙 기반으로 대조 — 벗어나면 자연어 설명을 카드에 노출하지 않고 숫자(risk_score)만 표시(안전한 폴백)

**Step E. 테스트**
- 정상 케이스: 카드에 1~2문장 설명이 근거 데이터와 일치하게 뜨는지 확인
- 가드레일 케이스: `key_factor`가 top3 밖으로 나오도록 강제해서 폴백(설명 미노출)이 실제로 동작하는지 확인
- 문구 확인: "참고용" 뉘앙스가 살아있는지(단정형 문장으로 과신 유발하지 않는지) — [[2-tech-research]] §6-3 XAI 과신 방지 원칙 그대로 대조

### 2. MAI 대화형 후속 질의 (①이 배포·QA 완료된 뒤에만 착수)

- 카드에 "더 물어보기" 버튼(`Action.ShowCard` + `Input.Text`) 추가 — [[63-approval-card-template]]의 반려 사유 입력 카드와 같은 패턴 재사용
- MD가 입력한 자유 질문을 1절과 같은 파이프라인(근거 조회 → Structured Output 생성 → 가드레일 검증)에 그대로 태워서 답변
- 무신사 MAI 벤치마킹 사례로 발표에 인용 가능([[4-differentiation-ideas]] 논의 5)

### 3. 하지 말아야 할 것

- 9/23 코어 체크포인트 통과 전에는 이 문서 어떤 단계도 착수하지 않는다.
- risk_score 계산 로직을 건드리지 않는다 — [[24-alert-rules]]가 SSOT, 임현제님 담당.
- `FashionAI.Api` 엔드포인트를 4개에서 5개로 늘리는 결정을 혼자 내리지 않는다 — 4-2절 원칙과 얽힌 팀 결정 사항.
- 완전 자동생성·확정형 문구를 카드에 노출하지 않는다 — 설명은 항상 "참고용 1줄"이고 승인/반려 최종 판단은 사람이 한다는 HITL 원칙을 그대로 지킨다.
- 새 벡터DB·별도 챗봇 서버 등 신규 서비스를 도입하지 않는다 — 기존 ERD 순회 + Structured Output만으로 끝낸다.
- ①이 실제 배포·QA까지 끝나기 전에 ②(MAI 후속 질의)를 먼저 시작하지 않는다.

## 결론 — 자주 헷갈릴 수 있는 것들

**Q. 이거 결국 챗봇 만드는 거 아닌가?**
아니다. ①은 카드에 붙는 정적 한 줄 설명이고, ②도 "더 물어보기" 버튼 하나짜리 후속 질의지 상시 대화형 챗봇이 아니다. 실제 RAG 챗봇은 이번 스코프에 없다는 원칙([[21-system-model]] 서론)은 그대로 유지된다.

**Q. 논의 5(정책 Q&A 코파일럿, 반려 사유 자동 제안, 정기 자동 리포트)는 왜 이 문서에 없나?**
아직 2주 스코프에 넣을지 선별이 안 된 논의 단계 항목([[4-differentiation-ideas]] 논의 5, `#todo/week0`)이라 설계가 확정되지 않았다. 이 문서는 이미 설계가 끝난([[21-system-model]] 부록 A) ①·② 두 건만 다룬다. 논의 5 항목을 실제로 채택하면 그때 별도 작업지시서를 만든다.

**Q. Azure OpenAI 리소스를 지금 미리 만들어놔도 되나?**
프로비저닝 자체는 미리 해둬도 무방하지만, 실제 호출 로직(Step C)은 9/23 이후 "호출 위치" 결정이 난 다음에 붙인다. 리소스만 미리 만들어두는 건 이 문서의 "착수 조건"을 어기는 게 아니다.
