## 서론

이 문서는 형준님이 처음 맡는 RAG·자동화 롤 작업지시서다. "RAG"라는 이름 때문에 챗봇이나 벡터DB를 떠올릴 수 있는데, **이번 스코프에 실제 RAG 챗봇은 없다**([[21-system-model]] 서론에 이미 확정된 결정). 실제로 할 일은 **Power Automate로 만드는 승인 알림 자동화**다 — Dataverse에 재발주 추천 레코드가 생기면 Teams로 카드를 보내고, 승인/반려 버튼을 누르면 결과가 다시 Dataverse에 기록되는 흐름 전체다.

지금 단계에서 헷갈릴 수 있는 것들(어디까지가 내 일인지, 최민님이 말한 "C# 붙이기"가 나랑 관련 있는지)은 [결론](#결론--자주-헷갈릴-수-있는-것들)에 따로 정리했으니, 막히면 거기부터 확인할 것.

## 본론

### 1. 지금 전체 그림에서 내 자리

**(2026-09-16 갱신)** [[25-execution-design]] 2절 기준으로 RAG·자동화 롤은 이제 **형준님이 실행 전체**를 맡는다 — 나경은 총괄(크로스커팅 계약 관리·설계 검수·체크포인트 운영)로 물러나고 직접 구현하지 않는다. 최민님 인프라/백엔드 범위 확장([[42-work-order-choimin]] 6절)·임현제님 ML 마무리로 팀 전체 작업량이 재조정되면서 나온 결정이다.

| 구분 | 내용 | 담당 |
| --- | --- | --- |
| Adaptive Card 템플릿(2-2절) | Teams에 뜨는 카드 UI/필드/버튼 JSON | **형준 (지금 시작)** |
| Power Automate Cloud Flow 본체(2-2·2-3절) | Dataverse 트리거 → 카드 발송 → 응답 대기 → Dataverse 업데이트 | **형준** (카드 완성 후 이어서) |
| 2-5·2-6절 스트레치(자동승인 SLA, 긴급 알림) | 9/23 체크포인트 통과 후에만 착수 | **형준** (그 전까지는 손대지 않음) |

즉 카드 한 장(Step 1)에서 끝나는 게 아니라, 그걸 실제 동작하는 승인 플로우로 만드는 것까지가 형준님 담당이다. 처음 다뤄보는 도구라 막막할 수 있는데, 아래 순서대로 하나씩 가면 된다 — 막히는 지점마다 나경한테 바로 물어봐도 된다(총괄이라 설계는 계속 봐줌).

### 2. 할 일 — 순서대로

**Step 1. Adaptive Cards Designer에서 카드 템플릿 만들기**
- 접속: https://adaptivecards.microsoft.com (Microsoft 공식 디자이너, 로그인 불필요, 브라우저에서 바로 JSON 편집·미리보기 가능. 옛 주소 `adaptivecards.io/designer`는 도메인 이전으로 404 남)
- 카드에 넣을 필드는 `ReorderRecommendation` 테이블의 7개 필드에서 아래만 그대로 매핑([[22-feature-spec]] 확정 스키마, **새 필드 만들지 말 것**):
  - `sku_code` (SKU 코드)
  - `predicted_demand` (예측수요)
  - `recommended_qty` (추천수량)
  - `risk_score` (위험도 — 숫자 그대로 표시, 색상 강조는 선택사항이며 필수 아님)
- 버튼 2개(`Action.Submit`, `data`에 어떤 버튼인지 구분값 포함):
  - **승인** — 누르면 `status=Approved`로 넘어갈 값
  - **반려** — 누르면 사유를 고르게 함: 드롭다운(`Input.ChoiceSet`) 4종 + 자유입력(`Input.Text`) 병행 (사유 목록·자유입력 병행은 9-10 타운홀에서 이미 확정된 UX — 대시보드에도 같은 방식으로 구현돼 있으니 [[72-dashboard-spec]] 참고해서 문구만 맞추면 됨)
- 실제 값 채워서 미리보기: Dataverse `ReorderRecommendation`에 이미 520 SKU 데이터가 들어있으니, Power Apps에서 레코드 하나 골라서 그 값으로 카드 미리보기가 실제 데이터처럼 보이는지 확인

**Step 2. Power Automate Cloud Flow 본체 만들기**([[25-execution-design]] 2-2·2-3절)
- Power Automate 메이커 포털(make.powerautomate.com)에서 Dataverse 커넥터로 Cloud Flow 새로 생성 — 로우코드, 별도 배포 불필요
- 순서: Dataverse 트리거("행이 추가되면", `ReorderRecommendation` 테이블 지정) → "Post adaptive card and wait for a response" 액션에 Step 1 카드 JSON 붙여넣기 → 응답값(승인/반려 + 반려사유)에 따라 조건 분기 → Dataverse "행 업데이트"로 `status`(+반려 시 `rejection_reason`, `resolved_at`) 기록
- 막히면: Microsoft 공식 튜토리얼 "Power Automate approval flow with adaptive card"로 검색하면 거의 동일한 예제가 나온다 — 처음이라 낯설 수 있는데 로우코드라 코드를 직접 짜는 건 아니다

**Step 3. 테스트**([[25-execution-design]] 2-4절)
- Dataverse `ReorderRecommendation`에 테스트 레코드 하나 수동 추가 → Teams에 카드가 실제로 도착하는지 확인 → 승인/반려 각각 눌러보고 레코드 상태가 바뀌는지 확인
- 반려 자유입력 케이스도 따로 확인

**Step 4. 승인이력 화면과 카드 문구 맞춰보기**
- [[70-frontend]] 쪽 대시보드 승인이력 뷰와 카드의 반려사유 문구·용어가 같은지 대조 — 다르면 통일(나경·최민 API 응답 스키마 기준으로 맞춤)

**Step 5. (9/23 체크포인트 통과 후에만) 2-5·2-6절 스트레치**
- 담당자 부재 시 자동 의사결정(SLA 타임아웃)과 위험 알람 Urgent 우선순위 — 상세 설계는 [[25-execution-design]] 2-5·2-6절에 이미 확정돼 있음, 그대로 따라 구현하면 된다. **지금은 착수하지 않는다** — 코어(Step 1~4)가 9/23 이전에 안 끝나면 이 스트레치는 시작도 안 하는 게 원칙(순서를 바꾸면 코어도 못 끝냄)

### 3. 하지 말아야 할 것 (판단 기준)

- 새 Dataverse 필드를 만들지 않는다 — 7개 필드로 스키마가 이미 확정([[42-work-order-choimin]] 2절). 카드에 뭔가 더 보여주고 싶으면 필드 추가 대신 문구로 해결할 방법부터 찾는다.
- 새 서비스·커넥터(별도 챗봇 서버, 벡터DB, 새 Azure 리소스 등)를 도입하지 않는다 — Adaptive Cards Designer + Power Automate 로우코드 안에서 끝내는 게 원칙([[25-execution-design]] 작성 원칙).
- risk_score 계산 로직을 건드리지 않는다 — [[24-alert-rules]]가 SSOT이고 임현제님 담당.
- 애매한 UX 판단(문구, 버튼 배치 등)은 마음대로 정하지 말고 대시보드 쪽(나경·최민 확정안)에 맞춘다 — 이미 확정된 게 있는데 다시 새로 디자인하는 건 이 프로젝트 원칙(신기술·재설계 최소화)에 어긋난다.
- 막히면 "이거 맞나?"를 혼자 오래 붙들지 말고 나경에게 바로 물어본다 — 2.5주짜리 PoC라 판단 지연이 제일 비싸다.

## 결론 — 자주 헷갈릴 수 있는 것들

**Q. 최민님이 "RAG모듈 넘겨주면 바로 붙일 수 있을 것 같다"고 하셨는데, 이거 내가 지금 신경 써야 하나?**
아니다. 최민님이 말한 건 [[25-execution-design]] 2-1·2-2절의 **스트레치 항목**(카드에 "왜 이 추천이 나왔는지" 자연어 1~2문장을 Azure OpenAI로 생성해서 붙이는 기능)이다. 지금 형준님이 만드는 카드(7개 필드 + 버튼)에는 이 문장이 들어가지 않는다 — 이 스트레치는 **9/23 코어 체크포인트를 통과한 뒤에만** 착수하기로 이미 정해져 있다(순서를 앞당기면 코어도 못 끝낸다는 게 이 문서 전체의 원칙).

**Q. (참고용) "RAG 모델을 C#에 API로 연결한다"는 게 기술적으로 뭘 말하는 건가?**
Azure OpenAI는 그 자체가 REST API라서, 어디서 호출하든 결국 같은 엔드포인트를 부르는 것뿐이다. 현재 확정된 설계([[25-execution-design]] 2-2절)는 이 호출을 **Power Automate 안의 커넥터 액션**으로 하는 것이었는데, 최민님은 대신 **`FashionAI.Api`(C# 백엔드)에 엔드포인트를 하나 추가**해서 거기서 Azure OpenAI를 호출하는 방식을 제안한 것으로 보인다. 두 방식 다 가능하고 "어디서 부르느냐"의 차이일 뿐이지만, 이건 4절 "엔드포인트 4개로 제한" 원칙과도 맞물리는 아키텍처 결정이라 **지금 형준님이나 최민님이 각자 판단해서 바꿀 사안이 아니라 9/23 이후 팀 회의에서 확정할 사안**이다. [[25-execution-design]] 2-2절에 이 논의를 미확정 항목으로 기록해뒀으니, 그 시점 가서 다시 꺼내면 된다.

**Q. 내가 만든 게 최종본인지 어떻게 아나?**
Step 3(테스트)에서 실제 Teams에 카드가 뜨고 승인/반려로 Dataverse 상태가 바뀌는 걸 직접 확인하는 시점이 최종 확인 시점이다. 그전까지는 전부 초안으로 생각하고 편하게 수정해도 된다. 9/23 체크포인트 전에 여기까지(Step 1~4) 끝내는 게 목표.

**Q. Power Automate를 한 번도 안 써봤는데 혼자 할 수 있을까?**
로우코드 도구라 코드를 짜는 게 아니라 화면에서 트리거·액션을 순서대로 끼워 넣는 방식이다. Step 2에 적힌 순서(트리거→카드발송→분기→업데이트)를 그대로 따라가면 되고, 막히는 지점은 나경한테 바로 물어봐도 된다 — 나경은 실행에서는 빠졌지만 설계 검수·질문 대응은 계속한다.
