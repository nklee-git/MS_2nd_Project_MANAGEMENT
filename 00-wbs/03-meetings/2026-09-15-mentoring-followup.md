## 5. 안건 5 — Data Factory 유지 여부 재검토 (신규, 대표님 코멘트 계기)

**배경**: 대표님이 "Data Factory를 굳이 넣은 이유가 뭔가, Azure Functions로도 될 것 같다"는 코멘트를 줌. 팀 내부에서 바로 논의:
- **임현제**: 대표님 의견에 동의 — "현업에서 잘 안 쓰는 툴은 도태된다, 남들이 더 많이 쓰는 서비스를 쓰는 게 좋다"는 입장, Functions 전환에 무게
- **최민**: Data Factory 유지 희망 — 채용공고에 자주 언급되는 스택이라 이력서 한 줄로 욕심남. "다른 팀원이 필요없다고 생각하면 어쩔 수 없다"고 한발 물러섬
- **나경 잠정 결정**: 최민이 일단 Data Factory 기반으로 오케스트레이션을 시도 → 안 되거나 팀 합의가 바뀌면 Functions로 갈아타는 선택지를 남겨둠

- [ ] 위 잠정 결정 그대로 확정할지 재논의
- [ ] Functions 전환 시 아키텍처 초안 공유: 실시간 데이터 생성모듈(소규모) → Azure Functions → DB 적재 / Functions → Event Hub → Stream Analytics → Azure PostgreSQL(비용 문제 있음, [[23-cost-plan]] 검토 필요)
- [ ] DB 마이그레이션 방침 확인: 현재 Azure SQLite에 적재 중 → 데이터 규모 커지면 PostgreSQL로 마이그레이션 범위 확장(시점 미정)

**워크플로우 재배정 (데이터 적재 우선)** — 박형준은 customer·factory 테이블만 적재하면 끝나는 상태. 이후 순서:
1. 데이터 적재 이어받아 완료 — 담당: 나경 (형준 인수인계)
2. 배포 — 담당: 최민
3. 데이터 적재 끝나면 Databricks 후속작업 — 담당: 임현제

- [ ] 이 순서·담당자 이견 없는지 확인

## 7. 안건 7 — 역할 스위처 vs MSAL 로그인 고정 역할 (신규, Dataverse 대행 작업 중 발견)

**배경**: 나경이 Dataverse 테이블·Security Role 대행 작업을 진행하다가, 지금 대시보드의 "역할 스위처"가 로그인 계정과 무관한 **프론트엔드 드롭다운**일 뿐이라는 걸 확인함([[72-dashboard-spec]] C절·E절 — "실서비스라면 로그인 계정에 역할 고정, 지금은 발표용으로 드롭다운 노출" / "아직 실제 권한 시스템엔 미반영"). 즉 Dataverse에 `Reorder Approver`/`Viewer`를 만들어도 대시보드가 그걸 전혀 참조하지 않음 — [[72-dashboard-spec]] 오픈 이슈("역할 전환 스위처를 데모 임시 기능으로 둘지, MSAL 로그인 고정 역할로 처음부터 설계할지")가 아직 미결이라 생긴 문제.

**나경 의견**: 드롭다운(데모 임시 기능) 유지를 추천.
- 발표가 9/29로 임박해 로그인 기반 권한 시스템을 새로 짤 공수가 부담됨
- 라이선스 제약으로 실 계정이 1~2개뿐이라, 로그인 고정으로 가도 나머지 가상 인물(13명)은 여전히 가짜로 보여줘야 해서 실익이 적음
- 발표자료엔 "실서비스 전환 시 MSAL 로그인 고정 역할로 교체 예정"이라고 한 줄만 언급하는 걸로 대체
- 이 결정에 따라 Dataverse Security Role(`Reorder Approver`/`Viewer`) 세팅도 지금 당장은 보류 — 정의를 만들어봤자 대시보드가 안 쓰므로 우선순위 낮음

**팀 결정 (2026-09-15 회의 확정)**: Security Role + 로그인 고정 역할 작업 전체를 **완전 백로그로 이동**. 1차 프로젝트 때처럼 로그인 페이지까지 만드는 방식은 이번 일정(9/29 발표)엔 시간이 너무 오래 걸린다는 판단 — 재검토 시점 없이 백로그로 확정.
